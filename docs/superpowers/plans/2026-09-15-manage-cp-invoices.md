# Manage CP Invoices Page Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give Company staff a dedicated "Manage CP Invoices" list page (mirroring the existing "Manage TP Invoices" page) to browse, filter, view/print, and delete CP invoices — the invoice-cum-delivery-note documents generated by the CP purchase-order invoicing feature built earlier.

**Architecture:** Mirror `company/manage-tp-invoices.php`'s visual structure and filter/table pattern for a new `company/manage-cp-invoices.php`, scoped down to CP's simpler data model (no state/location cascade — a CP has no location hierarchy the way TP does). Add a new `company/delete-cp-invoice.php` handler that mirrors `delete-tp-invoice.php`'s transaction/CSRF/lock discipline but is invoice-record-only: it does not reverse stock, since the underlying `pl_godown_transfers` stock movement already has its own separate return/delete flow (built in an earlier feature) and duplicating that reversal logic here would risk the two flows conflicting. Wire the new page into the sidebar menu and cross-link it from the existing CP Purchase Orders page, matching how TP Invoices is discoverable from Territory Partner's menu.

**Tech Stack:** PHP (mysqli, prepared statements), MySQL/MariaDB, existing house HTML/Bootstrap/DataTables page scaffold.

**Spec:** No separate spec document — this plan was approved directly via in-chat design discussion (bounded task, not architectural). The design rationale is captured in the Global Constraints below.

## Global Constraints

- CP invoice deletion removes ONLY the `cp_invoices`/`cp_invoice_items` record and un-links the originating PO's `cp_invoice_id` (sets it to NULL) — it must NOT touch `channel_partner_purchase_orders.status`, `channel_partner_purchase_orders.transfer_id`, `pl_godown_transfers`, `pl_godown_transfer_items`, `stock`, `channel_partner_stock`, or any ledger table. Stock reversal is out of scope; use the existing internal-transfer return flow for that separately.
- The list page has no state/location filter cascade (unlike TP's page) — CP has no `partner_location_nodes` hierarchy; filter only by CP (channel partner), date range, and product type.
- No courier-charge or rewards-points columns/actions — those are TP-only concepts that don't exist on `cp_invoices`.
- Row actions are View/Print (link to the existing `company/cp-invoice-print.php`) and Delete only — no Edit, since CP invoices are system-generated on PO approval, not manually authored.
- Follow this codebase's existing self-migrating-guard-free pattern here: `cp_invoices`/`cp_invoice_items`/the `cp_invoice_id` column already exist from the prior feature (`shared/CpInvoiceSchema.php`), so this plan does not need any new schema migration.

## Task 1: `delete-cp-invoice.php` handler

**Files:**
- Create: `femi9/billing/company/delete-cp-invoice.php`
- Test: `femi9/billing/tests/DeleteCpInvoiceTest.php`

**Interfaces:**
- Consumes: existing `cp_invoices`/`cp_invoice_items` schema (from `shared/CpInvoiceSchema.php`, already deployed): `cp_invoices.id`, `cp_invoices.invoice_number`, `channel_partner_purchase_orders.cp_invoice_id`.
- Produces: POST endpoint accepting `invoice_enc` (base64-encoded `cp_invoices.id`) and `csrf_token`; on success, deletes the invoice record and its items, sets the originating PO's `cp_invoice_id` to NULL (leaving `status`/`transfer_id` untouched), and redirects to `manage-cp-invoices.php?deleted=1&inv=<invoice_number>`.

- [ ] **Step 1: Write `delete-cp-invoice.php`**

```php
<?php
ob_start();
include("checksession.php");
error_reporting(0);

if (($Login_user_TYPEvl ?? '') !== 'company') {
    header("Location: manage-cp-invoices?error=unauthorized"); exit;
}

// Require POST with CSRF — prevents GET-based re-triggering (back button, browser retry)
if ($_SERVER['REQUEST_METHOD'] !== 'POST') {
    header("Location: manage-cp-invoices?error=invalid"); exit;
}
if (empty($_POST['csrf_token']) || empty($_SESSION['csrf_token']) || !hash_equals($_SESSION['csrf_token'], $_POST['csrf_token'])) {
    header("Location: manage-cp-invoices?error=csrf"); exit;
}

$enc = $_POST['invoice_enc'] ?? '';
$inv_id = (int)base64_decode($enc);
if (!$inv_id) { header("Location: manage-cp-invoices?error=invalid"); exit; }

// Quick existence check before entering transaction
$s = $db_conn->prepare("SELECT id, invoice_number FROM cp_invoices WHERE id=? LIMIT 1");
$s->bind_param("i", $inv_id); $s->execute();
$inv = $s->get_result()->fetch_assoc(); $s->close();
if (!$inv) { header("Location: manage-cp-invoices?error=notfound"); exit; }

$inv_num = $inv['invoice_number'];

// ── Transaction ──────────────────────────────────────────────────────────
// Deliberately narrow: this reverses only the paper/invoice record, never
// stock. The stock movement behind this invoice is a real
// pl_godown_transfers row with its own existing return/delete flow — see
// internal_transfer_return_action.php — which already knows how to reverse
// partial or full stock correctly. Duplicating that logic here would create
// two independent reversal paths that could disagree with each other.
$db_conn->begin_transaction();
try {
    // Lock invoice row — prevents a second concurrent delete from racing
    $lock = $db_conn->prepare("SELECT id FROM cp_invoices WHERE id=? FOR UPDATE");
    $lock->bind_param("i", $inv_id); $lock->execute();
    $locked = $lock->get_result()->fetch_assoc(); $lock->close();
    if (!$locked) {
        throw new \Exception("Invoice no longer exists — may have been deleted by another request.");
    }

    // Un-link the PO so it doesn't keep pointing at a deleted invoice.
    // The PO's status and transfer_id are intentionally left alone — the
    // stock transfer behind it remains a real, valid record.
    $po = $db_conn->prepare("UPDATE channel_partner_purchase_orders SET cp_invoice_id = NULL WHERE cp_invoice_id = ?");
    $po->bind_param("i", $inv_id); $po->execute(); $po->close();

    $d1 = $db_conn->prepare("DELETE FROM cp_invoice_items WHERE cp_invoice_id=?");
    $d1->bind_param("i", $inv_id); $d1->execute(); $d1->close();

    $d2 = $db_conn->prepare("DELETE FROM cp_invoices WHERE id=?");
    $d2->bind_param("i", $inv_id); $d2->execute();
    if ($d2->affected_rows === 0) {
        throw new \Exception("Invoice was already deleted by another request.");
    }
    $d2->close();

    $db_conn->commit();
    header("Location: manage-cp-invoices?deleted=1&inv=" . urlencode($inv_num)); exit;

} catch (\Throwable $e) {
    $db_conn->rollback();
    error_log("[delete-cp-invoice] Failed: " . $e->getMessage() . " in " . $e->getFile() . ":" . $e->getLine());
    header("Location: manage-cp-invoices?error=db"); exit;
}
```
