### 4. Return flow — two more real bugs found & fixed
- **Stock-origin bug (CP-fulfilled returns)**: `cnote_finish.php` was crediting returned stock into a bogus `stock` table row (`user_type='company', user_id='company'` — not a real godown id) instead of back into the CP's own `channel_partner_stock`, because the CP-fulfilled invoice's `from_user_id` is the literal string `'company'`. Fixed: detect via `fulfilled_by_cp_id`, credit `channel_partner_stock` + `channel_partner_stock_ledger` directly (mirrors `delete-tp-invoice.php`'s own CP-stock reversal pattern). `ref_type` on that ledger table is a narrow ENUM with no `'return'` value — used `'transfer'` (existing convention from `tp-cnote-finish.php`).
- **Warehouse-bucket bug (Company-direct returns)**: `cnote_finish.php` defaulted to warehouse_id=2 (G1) when an invoice never recorded its own `warehouse_id` — true for every DM-order Shop Invoice, but *this* invoice type's stock was actually debited with no warehouse filter at all (the unassigned/NULL-warehouse bucket), so a return was silently splitting stock into a second, wrong bucket. Fixed: for `source_ms_order_id IS NOT NULL` invoices, explicitly use the NULL-warehouse bucket instead of the G1 default.
- **Pre-existing, unrelated crash**: `cnote_manage.php` (Company's "Manage Return" list) fatally crashed (exit 255, zero error output — `error_reporting(0)` + forced-off `display_errors` swallowed it) the moment any `from_usertype='customer'` return existed in history, because that branch builds SQL with zero `?` placeholders but still passes `[$invid]` to `db_q()`, which correctly rejects the param-count mismatch and returns `false` → `mysqli_fetch_array(false)` fatal. This silently cut off the whole list below that row — including where Shop Invoice returns would sort. Fixed with a one-line conditional on the params array. Found via this session's established `die()`-checkpoint binary-search technique (confirmed `error_reporting(0)` swallows fatals even with `display_errors` forced via CLI `-d` flags).

### 5. Draft creation no longer blocked by insufficient stock (significant fix)
`ms-order-invoice-add.php`'s Company-godown path used to refuse to even create the draft if the chosen godown didn't yet have enough stock ("Not enough stock at this Company Profile to invoice..."). Since a draft never deducts stock (only Submit does, via `StockService::deduct()`, which has its own hard floor-at-0 guard), this pre-check was pointless and defeated Auto Transfer's whole purpose — Auto Transfer only ever sees a Shop Invoice as demand once a draft *already exists*. Removed the pre-check; `StockService::deduct()` is still the real safety net at Submit time.

Corollary fix: `shop-user-invoice-submit.php` used to catch a `StockService` failure at Submit time and **just log it, then redirect to the print page as if nothing went wrong** — the invoice looked fully submitted while stock was never deducted. Now sets `$_SESSION['errorMessage']` and redirects back to the edit page instead. `shop-user-invoice-add.php` had **no mechanism at all** to display session messages (no SweetAlert block) — added one (same pattern as `wallet-history.php` etc).

Live-tested full cycle: draft created with 0 stock → shows in Auto Transfer demand → Submit blocked with a clear error (stock still 0) → stock seeded (simulating Auto Transfer) → Submit succeeds, demand correctly drops to 0.

### 8. Performance: this page (and several others) were taking 74s–120s+ to load
Root cause was **not caching** — two real DB-level bugs, both pre-existing patterns this session's new queries also followed:
1. Every join on an invoice id was wrapped in `COLLATE utf8mb4_general_ci` on **both** sides (added historically to survive a collation mismatch after some past DB reimport). Wrapping an indexed column in `COLLATE()` makes it non-sargable — MySQL can't use the index, forcing a full scan of tables now at 66k–185k rows. Measured: one query went from **74s → 0.04s** just by not casting. Fixed with `_teamTargetCollationCast()` — checks `information_schema` once per request whether the relevant columns' collations have actually drifted apart, and only pays the `COLLATE` cost when that's genuinely true (self-healing if a future reimport reintroduces the mismatch).
2. `user_invoice.source_ms_order_id` (this session's own new column) and `ms_orders.order_id` had **no index at all**. Added both (`idx_source_ms_order_id`, `idx_order_id`).
- Result: `ms-team-shop-view.php` full page load went from 120+ seconds (timeout) to **~1.6 seconds**.
- Same `COLLATE`-both-sides anti-pattern also exists in `dm-target-achievement-export.php`, `remapping-tp-ss.php`, `shared/TpApproverContext.php` — **not yet fixed**, flagged for later if those pages are ever reported slow.
