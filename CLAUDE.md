## Bug fixed (2026-11-26): Internal Transfer "Return" silently recorded success without actually moving stock at the destination godown — found via user-reported real case (Neksomo→Healthcare→LLP), fixed in code + reconciled on both local and live DB

### Root cause
Company stock was tracked as a single (non-warehouse-scoped, `warehouse_id IS NULL`) bucket per godown until warehouse-aware tracking (G1/G2/G3/HO, `warehouses` table) was introduced 2026-09-21. Transfers made **before** that date have `stock_ledger` rows with `warehouse_id = NULL` for both legs. `company/include/AutoTransferDemand.php`'s `auto_transfer_leg_warehouse()` (used by both `undo_auto_transfer()` and `internal_transfer_return_action.php` to recover "which physical warehouse did this leg actually use") reads that NULL back faithfully — which is correct in principle, **except** that by now the destination godown's real current stock for that product has since been fully split into warehouse-scoped rows, with no NULL-warehouse row left at all. When a "Return" is filed against one of these old transfer lines, `StockService::reverseTransferIn()` (the step that's supposed to *remove* stock at the destination) then looks for a stock row at `warehouse_id = NULL` — finds none — and returns `['success' => false, 'reason' => 'no_stock_row']`.

`company/internal_transfer_return_action.php` only ever checked for ONE specific failure reason (`'insufficient_stock_to_reverse'`) on that call, and never checked `StockService::reverseTransferOut()`'s result at all (the step that restores stock at the *source*). A `'no_stock_row'` failure therefore went completely unnoticed — the code still incremented `returned_qty`, wrote the `internal_transfer_return` snapshot row, and committed the transaction, **even though the destination godown's real stock was never actually reduced**. Net effect: a "Return" looked fully successful in the UI/reports, but the physical stock just sat exactly where it was.

User-reported real case: a Healthcare→LLP leg's Return (and the paired Neksomo→Healthcare leg's Return) both "succeeded," but FEMI NAYAN LLP's G1 stock never dropped — confirmed via direct data tracing (see below) that this is exactly the above bug, not a one-off.

A full system-wide audit (all 81 `internal_transfer_return` rows ever created, every `(tempid, product_id)` group, comparing claimed returned qty against the actual `SUM(stock_ledger.qty WHERE action='transfer_in_reverse')`) found **exactly 7 broken lines, all the same Healthcare→LLP direction, nothing else anywhere in the system**:

1. Deducted the exact shortfall from `FEMI NAYAN LLP`'s **G1** warehouse stock (`stock` table, `user_id` = LLP's `company_godown` id, `warehouse_id` = the id with `code='G1'`), with a `transfer_in_reverse` ledger row for the audit trail.

3. `returned_qty` / `internal_transfer_return` snapshot rows were **left untouched** — the Return itself (Healthcare restore + Neksomo credit) was conceptually already correct and complete; only the LLP-side physical deduction had silently failed.

### Code fix — prevents this from ever silently recurring
`company/internal_transfer_return_action.php`: both `StockService::reverseTransferOut()`'s result (previously never checked at all) and `StockService::reverseTransferIn()`'s result (previously only checked for `'insufficient_stock_to_reverse'`) are now checked for **any** failure — either one failing now rolls back the whole Return and shows a clear "reconcile manually" error, instead of silently committing a Return that never actually moved stock.

`company/include/AutoTransferDemand.php`'s `undo_auto_transfer()` had the identical gap (its `reverseTransferOut()` calls for both legs were never checked) — fixed the same way. Its `reverseTransferIn()` calls were already checking for any failure, so those were already safe.

`company/internal_transfer_delete.php` (the "Delete" button on a transfer line — distinct from "Return") had the identical pair of gaps (`reverseTransferOut()` unchecked, `reverseTransferIn()` only checked `'insufficient_stock_to_reverse'`) — found via a full audit of every `reverseTransferOut()`/`reverseTransferIn()` call site in `company/`, fixed the same way. Two other call sites audited and confirmed already safe, no change needed: `company/demofree_delete.php` (already checks + falls back to `credit()` if no stock row exists) and `company/include/RawMaterialBundles.php` (already checks both for any failure).

## Conventions carried over from earlier sessions (still relevant)
- **Self-migrating schema pattern**: any new column is added by each consuming file itself (`SHOW COLUMNS ... LIKE` then `ALTER TABLE ... ADD COLUMN`), not a one-time migration script — except genuinely new tables (like `tp_daily_assignments`), which do get a one-time `.sql` file that must be run manually once. This session extended the pattern to **self-migrating indexes** too (see TP Invoice Amount performance fix below) — same `SHOW INDEX ... WHERE Key_name=...` check, then `ALTER TABLE ... ADD INDEX` if missing.
- **Credential handling**: never `grep`/`cat` DB credentials out of `config.php` directly. Instead write a standalone scratchpad PHP script that `require_once`s `femi9/billing/shared/env-loader.php` and connects via `mysqli_connect($_ENV['DB_HOST'], ...)`. Never print credential values — only query results. Correct env var names are `DB_HOST`/`DB_PORT`/`DB_USERNAME`/`DB_PASSWORD`/`DB_NAME` (not `DB_USER`/`DB_PASS` — tripped this up once this session).
- **No live DB access** — only local XAMPP DB (separate, sometimes out-of-sync dataset — confirmed this session to be live/current enough for October/November 2026 data, used for several of the above tests). When a live-only data question comes up (e.g. "who currently holds this location"), write a small read-only diagnostic PHP script (same env-loader pattern) and hand it to the user to upload/run on the live server themselves, then relay the output back — don't guess.

### Fix: `shop.state_id`/`district_id`/Taluk dual-reference-system bugs (Edit Shop empty dropdown investigation)
Investigating why "Edit Shop" showed an empty District dropdown uncovered **three separate instances of the same bug class** — a column assumed to reference one id-space but actually/sometimes populated from an incompatible one:
1. `shop.district_id` — sometimes broken/stale (already known from an earlier session), sometimes a real-but-wrong value surviving a Firka reassignment (this session's broadened single-district-TP fallback, above).
2. `shop.state_id` — should be a `state` TABLE id (7=Tamilnadu, 18=Karnataka) but was often populated with `partner_location_nodes` ids (Tamilnadu=2) or garbage, confirmed via `shared/ShopInvoiceData.php`'s own comment and GST-calculation code's explicit `state_id===2` legacy-bug marker. Fixed going forward via new `territory-partner/include/ShopStateIdResolver.php`'s `resolveRealStateId()` (converts a submitted `partner_location_nodes` state id to the real `state` table id via name-match), wired into `shop-action.php`/`shop-edit-action.php`.
3. `OrderTpBridge.php`'s own district_id resolution (legacy `district` table) — see above.
- `territory-partner/geo_layers.php`'s `$depthToField` mapping was `[2=>state_id, 3=>district_id, 4=>taluk_id, 5=>firka_id]` — wrong, since Division sits at depth 4 (inserted into the hierarchy after `shop` only got 4 location columns with no `division_id`). This silently corrupted Division's id into `taluk_id` and Taluk's id into `firka_id` on every single Add/Edit Shop save, while the real Firka (depth 6) was dropped entirely. Fixed to `[2=>state_id, 3=>district_id, 5=>taluk_id, 6=>firka_id]` (depth 4 intentionally skipped).
- `shop-edit.php`'s dropdown-init JS hardened to validate a saved geo id against the real rendered options before trusting it, falling back to single-option auto-select otherwise — fixes the empty-dropdown symptom for any shop still carrying old garbage data.
- **One-time live-DB fixes written** (both re-derive fresh from `district_id`, don't trust any existing stored value): `fix-single-district-tp-shop-districts-20261201.sql` (district_id backfill for single-district TPs) and `fix-shop-state-id-20261201.sql` (state_id backfill, both local DB and the diagnostic query confirmed ~28,914–28,996 affected rows locally).
- **`fix-shop-state-id-20261201.sql` hit a live-only COLLATE error** (`Illegal mix of collations (utf8mb4_general_ci) and (utf8mb4_unicode_ci) for operation '<>'`) that never appeared locally. Root-caused via a diagnostic `information_schema.COLUMNS` check (confirmed every relevant column — `shop.state_id`/`district_id`, `state.id`/`st_name`, `partner_location_nodes.id`/`name` — is actually `utf8mb4_general_ci` on both local AND live, so the column schemas were never the mismatch) plus `SHOW VARIABLES LIKE 'collation%'` (confirmed live's `collation_connection = utf8mb4_unicode_ci` while `collation_database`/`collation_server` are `utf8mb4_general_ci`) — the `CAST(rs.id AS CHAR)` in the script's `WHERE ... != CAST(...)` clause picks up the **connection's** default collation, not any column's, so it only ever surfaced on live (whose phpMyAdmin session happens to negotiate a different connection collation than local's). Fixed by adding an explicit `COLLATE utf8mb4_general_ci` on both sides of that comparison (the join's own `=` comparison needed no fix — column-to-column, already matching).
- **After the COLLATE fix, re-running on live found 0 rows to fix** — diagnosed via a direct sample query (`state_id` vs freshly-derived `correct_state_id` for 10 real live rows) confirming live's `shop.state_id` was **already correct** for every row with a resolvable district. Conclusion: this particular corruption was **local-DB-only** (likely from an earlier local test/reimport session), never a real live-data bug — this script does not need to be run on live. Lesson for future sessions: don't assume a bug confirmed on local DB necessarily exists on live too, especially after the DB-reimport/local-drift issues already in persistent memory — verify independently on live before writing it off as "needs fixing there too."
