## Major behavior change (2026-11-17): DM Get Order Shop Invoices now gate ALL stock release through Auto Transfer
User explicitly asked (after understanding it diverges from the existing TP/CP PO pattern — confirmed via AskUserQuestion) that every DM Get Order Shop Invoice (`source_ms_order_id IS NOT NULL`) must show up in Auto Transfer before its stock ever moves — even when the chosen warehouse already has enough stock. Non-DM Shop Invoices (plain company-created, no source_ms_order_id) are unaffected — unchanged immediate-deduct-on-Submit behavior.

**Submit side** (`company/shop-user-invoice-submit.php`): for DM-order invoices, Submit now ONLY saves the invoice header/items — no `invoice-stock-update.php` include, no `reverseAll()`, no receipt insert. The payment fields the form still collects (`receivedamount`/`receipt_method`/`receipt_remarks`) are stashed on new self-migrating `user_invoice` columns (`pending_received_amount`, `pending_receipt_method`, `pending_receipt_remarks`) for later use. Redirects to `ms_prorders.php` with a clear message instead of the print page (nothing to print yet).

**Release side** (`company/include/AutoTransferDemand.php` + `company/internal_transfer_auto_action.php`): two mechanisms, both needed —
1. `record_auto_transfer_partial()`'s existing 'shop' branch now also calls a new `_auto_transfer_release_shop_invoice_line()` helper — the moment a Shop Invoice line gets credited from a successful Neksomo→Healthcare→LLP replenishment leg, it performs the REAL local `StockService::deduct()` from the invoice's own `warehouse_id`/`from_user_id` bucket, and once every line of that invoice is fully covered, writes the real receipt (using the stashed pending_* fields) — this is the one thing that makes an invoice disappear from Auto Transfer's demand list for good.
2. **Critical gap found and fixed**: that credit-loop path only runs when the per-product replenishment leg actually moved something (`$legOneQty > 0`) — if Neksomo has zero stock but the invoice's own warehouse (e.g. G1) ALREADY has enough, the loop `continue`s and Shop never gets released at all. Added a new independent function `release_shop_invoices_from_existing_stock()`, called once per "Transfer Now" click regardless of what the replenishment legs did, that walks every outstanding Shop Invoice line and releases whatever it can straight from that line's own warehouse's CURRENT stock (via `StockService::getClosingQty()`), calling `record_auto_transfer_partial()` for whatever it can cover. This is what actually handles the common case (G1 already sufficient).

Live-tested the full chain via session-simulation + direct function calls (not just unit tests): created a draft invoice (4 lines, one deliberately short on stock) → Submit confirmed zero stock/receipt touch, correct pending_* stash → ran the release function, confirmed 3/4 lines deducted (real `stock_ledger` entries) and the receipt correctly WITHHELD because one line was still short → topped up the short line's stock (simulating a real transfer arriving) → re-ran, confirmed the last line deducted and the receipt created with correct amounts/payment method. ## Conventions carried over from earlier sessions (still relevant)
- **Self-migrating schema pattern**: any new column is added by each consuming file itself (`SHOW COLUMNS ... LIKE` then `ALTER TABLE ... ADD COLUMN`), not a one-time migration script — except genuinely new tables (like `tp_daily_assignments`), which do get a one-time `.sql` file that must be run manually once. This session extended the pattern to **self-migrating indexes** too (see TP Invoice Amount performance fix below) — same `SHOW INDEX ... WHERE Key_name=...` check, then `ALTER TABLE ... ADD INDEX` if missing.
- **Credential handling**: never `grep`/`cat` DB credentials out of `config.php` directly. Instead write a standalone scratchpad PHP script that `require_once`s `femi9/billing/shared/env-loader.php` and connects via `mysqli_connect($_ENV['DB_HOST'], ...)`. Never print credential values — only query results. Correct env var names are `DB_HOST`/`DB_PORT`/`DB_USERNAME`/`DB_PASSWORD`/`DB_NAME` (not `DB_USER`/`DB_PASS` — tripped this up once this session).
- **No live DB access** — only local XAMPP DB (separate, sometimes out-of-sync dataset — confirmed this session to be live/current enough for October/November 2026 data, used for several of the above tests). When a live-only data question comes up (e.g. "who currently holds this location"), write a small read-only diagnostic PHP script (same env-loader pattern) and hand it to the user to upload/run on the live server themselves, then relay the output back — don't guess.
